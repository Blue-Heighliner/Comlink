# Transport

`IPeerTransport` is the layer between the peer services (`PeerService`, `ClientPeerService`, `ServerRoutingService`) and the wire. It connects out to `ConnectionPoint`s, listens for connections from others, moves opaque, already serialized messages over the resulting `PeerConnection`s, and reports connections coming and going. A `ConnectionPoint` is either an IP host and port or a MicroGate serial port name and HDLC address, and the transport, not the service, picks the medium. A point says nothing about who is at the other end; that is worked out as the connection forms (see [Identification.md](Identification.md)). The services therefore have no knowledge of TLS, MSMT, HDLC, or serial ports, and a node can reach some users over IP and others over a cable at the same time.

## Shape

`PeerTransportFactory` builds a `CompositePeerTransport` from two halves:

- `MsmtPeerTransport` adapts an `IMsmtSessionPeer` for IP points (mutually authenticated TLS, session connections opened by `Connect` and cached per point, plus the ones remote nodes open to the listener).
- `SerialPeerTransport` holds one persistent `SerialLink` per distinct serial point for MicroGate cables.

The composite routes each `Connect` by `ConnectionPoint.IsSerial` and each `Request` by the connection's own medium, and merges the `Received`, `Connected`, and `Disconnected` streams of both halves. `Connect` returns the connection to a point, opening it first when there is none, and a `Request` is always made over a `PeerConnection`, whichever end opened it. A `Request` completes only when the remote node has acknowledged the message, and throws if it could not be delivered; both halves honor that same contract, which is what lets the services stay medium agnostic.

When the host has turned packetization on with `Packets`, the factory wraps the composite in a `PacketizingPeerTransport` (a decorator with the same contract, scheduling packets per connection), so every peer, client and server service gets packetization without knowing about it. Outermost it always adds a `HandshakePeerTransport`, which identifies each connection before publishing it and, when an initial frame is configured, runs that exchange first; an initial packet exchange, when configured, is run by another `HandshakePeerTransport` beneath the packetizer. Neither adds anything to what crosses the connection (see [Identification.md](Identification.md#initial-packet-and-frame-exchange)).

The IP half needs an identity certificate for the current user, which is unavailable before a user is installed or on a node that never uses IP. In that case the factory logs a warning and builds the composite without it: IP requests then fail with `IOException` while serial keeps working. This is what allows a serial-only node to run with no certificates at all.

## Points and connections

A `ConnectionPoint` with a `SerialPort` is serial; `IpAddress`/`Port` are then ignored. `SerialAddress` is this node's HDLC station address (default 255) and `RemoteSerialAddress` the address of the node at the other end of the cable (default 254); they must differ, and the two ends must use the values the other way round (one end `1` and `2`, the other `2` and `1`). A link starts the HDLC peer on the port with the options from `IEngineController.HdlcOptions`, which readies the device, then connects it with these two addresses, which forms the HDLC connection. A serial point may also list the users it may reach (`OtherRemotes`, each a user and its HDLC address); the connection is identified as the user at the address that answered (`UserAt`), since a serial link carries no certificate, and without a match it is named after its port. Points compare equal by `Key`: IP by host (case-insensitive) and port, serial by port name (case-insensitive) and address. Two points naming the same port and address share one link.

A `PeerConnection` carries a connection info, an `IpConnectionInfo` or `SerialConnectionInfo` (the remote host, port and certificate names for IP; the port and address for serial), whether the remote node opened it, the point this node dialed (none for an inbound one), and, once identified, the `UserIdentity`. Its `Key` is the point's key for one this node opened and unique otherwise, so schedulers and other per-connection state never mix two connections up. Over IP the connection knows its certificate; over serial a cable joins exactly two nodes and is opened from both ends, so a serial connection is always reported as the link this node opened, with no certificate, and its user comes from the port and address or from a connection message.

There is no authentication or encryption on a serial link. The trust model is the physical cable: only configure a serial point for a port whose far end you control.

## Serial links

The MicroGate device speaks HDLC in asynchronous balanced mode: both ends are equals, either may initiate, and frames arrive in order without gaps while the link is up. A HDLC peer is single use and a frame carries at most about 4 KB, so `SerialLink` adds only a connect loop and send ordering on top. It adds nothing to what is sent: **each serialized frame or packet is exactly one HDLC information frame, byte for byte, with no header, fragment number, reply or any other data of this software's own**, so a system that does not run it can take part. A payload that does not fit one frame (`MaxInfoField`) fails to send, with the reason logged: the engine's packet size (`PacketSize`) is the only limit it applies, so on a serial network it must not be larger than `MaxInfoField`:

- **Connect loop**: the link creates a peer, starts it (which completes only once the far end answers), publishes `Connected`, and waits for the peer to end. On loss it publishes `Disconnected`, and after a short delay creates a new peer. A device that cannot be opened is retried the same way, with a single warning logged per outage instead of one per attempt.
- **Opening**: a serial link starts connecting the first time its point is connected to, which every role does at startup through the connection monitor. `Connect` fails while the link is not up (the monitor retries), and the link keeps reconnecting on its own.
- **Framing**: none. Every received information frame is published to `Received` verbatim as one payload; packets that make up a larger payload are reassembled above this layer by the packetizer.
- **Request semantics**: `Request` returns `true` once the frame has been handed to the device, which HDLC itself delivers reliably and in order; the remote node cannot reject it, as nothing but the payload is exchanged. It throws `IOException` when the link is down or drops while sending, and returns `false`, having sent nothing and logged the reason as an error, for a payload larger than one frame. `Transmitted` fires at the same moment.
- **Ordering**: sends are serialized, and when several wait the highest `PeerSendOptions.Priority` goes first (first come, first served among equals), as over MSMT. Packets, when configured, are small, so priority orders them finely.
- **Heartbeats**: none are sent over a serial link; HDLC reports the state of its own link, and the connection monitor counts the point as up while that link is connected.

## Configuration

Serial points come from a user's `Hdlc` ports and its links in `Hdlc` mode: the node opens one point per port named in its `Hdlc.Ports` (every available port for `*`), at its own `Hdlc.Address`, and each point tries the `Hdlc.Address` of every HDLC-linked user in turn (`ConnectionPoint.OtherRemotes`) until the far end of that cable answers; the connection is identified as the user at the address that answered. The link is stated on both nodes that share the cable, and, because the one cable already carries both directions, a client whose server is serial needs nothing more. Because each node has its own configuration, the same server can be an IP point on one node and a serial point on another.
